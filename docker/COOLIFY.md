# LiveContext Jada on Coolify

## Why this differs from upstream

The fork includes custom LLM endpoint URLs, configurable custom API authentication,
MCP key scope validation, and chat reconnection fixes. The upstream v0.2.15 backend
and frontend images do not contain those changes. Both Compose entry points build
these two services from the checked-out Git source with CE/embedded authentication.
Unchanged bridge and renderer services retain their version-pinned upstream images.

## Git-based application settings

- Repository: `https://github.com/itsablabla/livecontext-ce-jada`
- Branch: `main`; record the exact deployed commit in the deployment log.
- Build pack: **Docker Compose**, not Dockerfile or Nixpacks.
- Base directory: `/`
- Docker Compose location: `/docker-compose.coolify.yml`
- Raw Compose deployment: **off**. Coolify must generate its proxy/network labels.
- Preserve repository: **on**, for the catalog and SearXNG bind-mounted configuration.
- Build sequentially on smaller hosts: `docker compose --parallel 1 build`.
- Enable **Use Build Secrets** and disable **Inject Build Args to Dockerfile**.
  Required Compose variables must be marked both build-time and runtime in Coolify:
  the build-time flag makes them available for Compose interpolation, while secret
  mode avoids passing their values as Docker build arguments. The Dockerfiles do
  not consume these runtime secrets. Do not enable automatic ARG injection.
- Configure a domain only for `gateway`, with internal port `80`.
  Leave `frontend` and `livecontext` without public domains.
- Do not add host port mappings. The Coolify proxy can already occupy port 8080.
- Keep automatic deployment off until acceptance testing is complete.

Use an AMD64 server for the bundled Chrome browser image. Budget at least 12 GB RAM
for source builds and approximately 9 GB for configured runtime ceilings. These are
deployment sizing recommendations, not a guarantee of workload capacity.

## Required environment values

Set these as secrets in Coolify, not Git or Docker build arguments. Mark them
build-time and runtime with the settings above so Compose validation can run:

```text
DB_PASSWORD=<unique random password>
MINIO_ROOT_PASSWORD=<unique random password>
GATEWAY_FILTER_SECRET_KEY=<unique random secret>
STORAGE_SHOWCASE_HMAC_SECRET=<unique random secret>
WEBSEARCH_GATEWAY_SECRET=<unique random secret>
WEBSEARCH_CDP_JWT_SECRET=<unique random secret>
SEARXNG_SECRET=<unique random secret>
BOOTSTRAP_PASSWORD=<unique setup access password>
BOOTSTRAP_AUTH_REALM=Setup
PUBLIC_BASE_URL=https://jada.example.com
GATEWAY_PUBLIC_URL=https://jada.example.com
APP_VERSION=jada-<deployed revision>
```

Neither public URL may have a trailing slash or an internal container port suffix.
Both origins are the same. Only the Coolify gateway domain configuration includes `:80`.
Encryption and embedded-auth signing keys are generated by the native entrypoint
and persisted in `livecontext_keys`. Back up that volume together with PostgreSQL
and MinIO; replacing it can make stored credentials unreadable.

SearXNG reads `SEARXNG_SECRET` over the example file's default. The browser gateway
and CDP token secrets must match between backend and websearch.

## First access and model setup

The gateway protects first access with temporary HTTP authentication. The username
is `jada-setup`; retrieve `BOOTSTRAP_PASSWORD` from the application's Coolify
environment variables. This is separate from the LiveContext account password.
The first registered LiveContext user becomes administrator. Complete that setup
before removing temporary protection; do not expose an unclaimed instance.
After the owner has registered, set `BOOTSTRAP_AUTH_REALM=off` and redeploy to use
normal LiveContext authentication. Basic authentication is a bootstrap gate, not an
ongoing API policy: it conflicts with application Bearer Authorization headers.
Do not switch it off before an administrator account exists.

In Settings > AI providers, save a provider key and, if needed, its full request
endpoint (for OpenAI-compatible APIs, typically ending in `/v1/chat/completions`,
not only `/v1`). URL safety checks reject private-network targets. An endpoint
override changes a URL, not the selected provider's wire protocol.

Browser-agent and coding-CLI integrations have their own provider implementations.
Do not assume the backend's custom endpoint override configures those adapters.
Test each with the actual chosen provider before claiming complete model support.

## Verification and upgrades

General chats without an explicit iteration setting default to **100 iterations**.
The backend fallback and Coolify Compose's
`CONVERSATION_AGENT_MAX_ITERATIONS: "100"` deliberately agree with the chat UI.
This setting survives restarts and source redeployments. Explicit conversation
and agent limits still take precedence. User/workspace defaults seed new
conversations; changing them does not retroactively rewrite existing chats.
An existing chat with no iteration key uses the backend fallback.

Run `python3 docker/tests/compose.test.py` with PyYAML installed. For native Compose
validation, strip the Coolify-only `exclude_from_hc` service key first; Coolify
removes it before calling Docker. `minio-init` is a successful one-shot, not a
long-running healthy container.

Acceptance requires all ten persistent services healthy and the initializer exit
code zero; HTTPS and runtime-config correct; login and session refresh; a chat
completion and reconnect; custom API auth; scoped MCP key rejection; search and
browser execution; screenshot/PDF rendering; and persistent data across redeploy.
Health checks alone do not prove LLM execution, OAuth, email delivery, or backups.

Never run `docker compose down -v` during upgrades. Review database migrations
before rollback and restore a coordinated backup when schema compatibility requires it.
